# Agentic resources: implementation plan (pre-code revision 2)

Baseline: upstream `main` ca47a952 (2026-10-14), isolated worktrees `feat/agentic-resources-unified` and `feat/all-resource-builder`. This is a two-PR product change, NOT a new ARD protocol or migration of component tables. Existing `/agents/*`, `/components/*`, `/resources/*`, and canonical namespace/slug deep links remain valid. Issue #1792 (last comment 2026-10-11) requests **agent** builder parity; it does not cover a standalone resource authoring entry point.

## Issue drafts — NOT for publication before human review

### Issue A: Make Agentic Resources a coherent six-kind workspace
**Problem:** The product calls agents and five standalone component kinds Agentic Resources but browsing, actions, and detail routes can feel like separate products. People need to recognize the kind, discover it, and continue its own lifecycle without relearning navigation. **Scope:** six-kind discovery and search, single resource entry and kind selection, route and action clarity, owner submissions, contextual navigation across detail pages. Preserve native records, authorization, statuses, canonical IDs, review semantics and old URLs. **Acceptance:** a newcomer can find each kind, filter/search it, find owned drafts, use kind-specific available actions, and return to the same context using keyboard and narrow viewport. Logged-out discovery works. No cross-kind permission bypass or ARD change. **Out of scope:** editor field parity; addressed by Issue B. Screenshots, six-kind browser tests, dark/light and responsive proof required.

### Issue B: Build and edit agents and all five standalone resource kinds in one authoring workspace
**Problem:** The Builder is branded for agents alone while five kinds can be submitted in a dense dialog without a durable dedicated workflow; lifecycle and validation are uneven. **Scope:** choose kind, create and resume drafts, edit and validate each kind, preview relevant payload, submit for review; compose components into agents, server-backed harness compatibility, meaningful error recovery and owner-only actions. Reuse existing models/routes; implement only supported operations and add focused server validation where incomplete. **Relationship to #1792:** #1792 is agent-builder CLI parity and agent draft/edit/version issues. This issue adds standalone MCP/skill/hook/prompt/sandbox authoring and a coherent cross-kind entry point; it should reference, not replace, #1792. Implement overlapping agent parity once, not duplicate interfaces. **Acceptance:** end-to-end owned draft→edit→submit for each kind; no false preview or publish language; clearly mark CLI-only or unsupported features; review status and version path visible; tests and screenshots for all kinds. **Out of scope:** new ARD format, universal version abstraction, immediate auto-approval.

2. Owner selects each kind from a clear creation entry point; enters minimal draft fields; save, reopen after reload, edit, see actual validation errors, submit for review, navigate to resulting detail, understand pending status and next review action. 3. Agent owner selects supported harness(es), adds approved components of all five kinds, adds prompt or prompt component, validates and saves/reopens/submits; edits approved agent via version route rather than mutating approved release. Component compatibility and owner/team visibility enforced by server.

5. Desktop/narrow, keyboard, dark/light, server failure and unsaved navigation tested interactively. Screenshots of materially affected screens retained outside git until PR review. Run frontend lint/typecheck/build, backend focused and full tests, live `make rebuild` and Playwright with six-kind coverage.

### Decisions and PR boundary

Do not fan out six unbounded list calls. Add explicit handoffs between the surfaces and type/action labels; PR1's creation entry points to existing `/agents/builder` for agents and the current per-kind component dialog for others, without claiming unified authoring yet. PR2 owns a guarded `/build` authoring entry/chooser and standalone forms plus #1792's overlapping agent builder improvements *in the existing agent URL*, not a second agent form. PR2 will cite #1792 as authority for agent-specific parity and list delivered versus deferred fields in its diff. Issue B remains about standalone authoring plus shared builder entry; avoid promising full CLI parity under its own issue. PR2 is stacked on PR1 (`base: feat/agentic-resources-unified`); once PR1 merges rebase PR2 onto main, reread PR2-only diff and rerun all checks. Never silently amend PR1's navigation from PR2.

Route compatibility: `/agents/{uuid}`, `/agents/{namespace}/{slug}`, `/components/{uuid}?type=mcps`, `/components/{type}/{namespace}/{slug}`, `/resources/agents?search=...&view=my`, `/agents/builder?draft={uuid}`, `/resources/skills?folderListingId=...&folderVersionId=...&folderVersion=...` (all three are required for exact version restoration); invalid types redirect according to existing route; direct/reloaded unauthorized private/draft links return existing non-disclosing 404 for authenticated outsiders, login for unauthenticated callers (subject to public registry configuration), never leak other drafts. `/build` is not under `/resources/` because the public path allowlist accepts two-segment resource paths; authenticate `/build` via route guard and API auth. Preserve detail `?tab=edit` and exact skill-version parameters. When coming from a filtered catalogue, browser Back restores URL-backed kind/search/view/team/namespace and native scroll restoration when supported; provide a contextual return link only if a safe local browse origin exists (never redirect to arbitrary user-provided URLs). Direct/shared links use type-specific resource breadcrumb; do not promise a restored origin without one. `/discover` must migrate its query/filter state to typed URL search before promising Back restoration; otherwise preserve only the browser's actual state with honest copy. Include a direct-link reload test for the typed query. All breadcrumbs remain valid on reload.

Search budget: query only active kind via existing server-side search; debounce input, propagate AbortSignal from queryFn through registry.list to api fetch and retry path, preserve `X-Total-Count` in a paginated result contract and expose page/offset navigation for >50 results and extend `/my` server endpoints with search/filter applied **before** pagination and count, plus limit/offset and totals, so that no owned result is truncated. Client-side filtering a paginated owner page is explicitly insufficient. Every matching resource, including beyond page 1 and owned drafts, must be reachable; do not call a truncated list exhaustive. Never interpret an empty first page as no matches beyond page 1; test >50 fixtures and server search. PR1 must not introduce six-way fanout or fetch new full `/my` lists on every keystroke. If the existing API cannot paginate owner drafts, add server pagination and total metadata before claiming this journey complete; disclosure alone does not satisfy the acceptance criterion.

### Exact authorization, status and action contract
Guest with `public_registry_enabled=true`: approved public detail and catalog; disabled: sign-in gate. Private team listing visibility requires current membership; former member can lose read access even as submitter. Team membership alone does not grant edit; submitter/co-author/admin server checks do, subject to current team access. Team-create uses server role policy; reviewer action uses separate team/global review policy. Existing admin effective-permission functions return `owner` for components: treat admin edit as the documented override, not ordinary ownership; test admin write separately from review. `owner` is display metadata only. Show write controls only for server-returned permission where available; require API authorization on every write; unknown permission is read-only. `/my` is submitter-owned, not a comprehensive co-author workspace. For approved agents, create new version via `/agents/{id}/versions`, never PUT approved release. For draft/rejected/changes-requested agents, PUT `/{id}/draft`, then POST `/{id}/submit`; pending edits follow edit-lock rules. Generic component draft/rejected: PUT `/{id}/draft` then POST `/{id}/submit`; approved components use version/edit affordances already available on detail, never present the draft route as an in-place approved edit. Approved skill folder uses exact version candidate draft workflow; a pending folder must be withdrawn before edit. Archive/delete/fork and render/install are contextual detail actions; sandbox has **no install**; prompt render requires a persisted accessible listing. Success copy says 'Submitted for review', not 'Published', unless approval actually occurred. Review is separate from submit and may return rejection/changes requested; rejected authors can correct and resubmit. Confirm destructive actions, and do not present pending review as approval.

Edit locks for ordinary drafts prevent *other users* from editing for roughly 30 minutes, but do NOT prevent stale tabs from the same user overwriting work. Warn on concurrent tabs / local unsaved changes and never claim optimistic concurrency exists. On 409/locked/permission error, preserve form state and offer retry or reload without automatic overwrite. Skill folder uses observed revision: on conflict keep local files, surface exact version and revision and require explicit refresh/rebase. Never silently resubmit or overwrite an exact version.

### Six executable authoring contracts
| Kind | First save (server minimum) | Submission gate & real preview | Resume/error/version |
|---|---|---|---|
| Agent | `AgentCreateRequest`: valid name/version, owner, model_name, prompt OR prompt component even for draft **after fixing the current field-order validator to a model-level cross-field check**, with API tests for both paths | composition validation only checks IDs/scope; prompt/model/harness and actual installability must be separately checked; YAML review labelled configuration *summary*, not install-file preview without install endpoint | reload from `component_links` (not `components`), preserve pins/config; rejected correction→submit; approved→version endpoint; no unsupported guaranteed installer preview |
| MCP | name; draft accepts empty description/source | description + git URL or command or URL; display sanitized config summary, server analyze only on explicit request with SSRF guard | exact draft reopen, source missing inline error; approved version/action detail |
| Skill git/direct | name; mode and content may be incomplete draft | usable git URL (add missing normal draft-submit gate) or valid SKILL.md according to delivery mode; test ordinary and version-specific submit routes, do not imply CLI-only folder export/install on unsupported harness | normal draft endpoint for simple skill only; folder upload creates version manifest and uses separate route |
| Skill folder | folder `SKILL.md`, version and metadata for `/skills/folder-drafts` (not listing draft) | feature flag & manifest/revision gate; `/skills/{id}/versions/{version_id}/submit` with `observed_revision`; preview file tree, not executable behavior | reopen exact version, withdrawal for pending, rebase on conflict; disabled gate allows saving only and explains why submit unavailable |
| Hook | name; draft defaults event/handler | event, valid handler configuration/script enforced server-side on draft submit; show literal config only, no execution preview; show server-provided hook-capable harnesses | correction/submit via hook draft routes; optional filters advanced |
| Prompt | name; draft template can be empty | template and valid category enforced server-side on draft submit; saved-item render endpoint where permission allows; before save show template text, not claimed rendered preview | exact draft reopen; edit/submit; render only after persistence |
| Sandbox | name; draft defaults runtime and permits empty image | image + runtime-specific config **also on draft-submit** enforced by server, non-installable standalone; summarize network policy explicitly | exact draft reopen, correct failed validation, submit/review; no install button |

For every kind: draft fields and publish prerequisites visibly separate, persistent input labels, type-specific example and inline field errors, scroll/focus to first invalid field on submission, keep values after rejected mutation, announce success via status/toast and link to result. No universal 'validated' green state when only component IDs/scope were checked. Component harness compatibility derived from server `/config/harnesses` capabilities and server-provided required capabilities; sandbox support and installation gates must not be assumed solely from a checkbox. Agent components must be approved or owner-accessible as authorized by server; partial failure creating a child component never silently claims the agent saved too. Optional fields grouped in labelled accessible disclosures, required fields never hidden by default.

### Browser and quality contract
Kind choices use named links with `aria-current=page`, not faux ARIA tabs; list items use links rather than clickable divs. Browser Back and filters preserve URL state; kind change moves focus to selected kind link or new heading and announces kind/results; builder step change focuses new heading and announces step. Closing a dialog returns focus to its opener. Changing filters announces result count without shifting focus from search. First invalid control receives focus and `aria-invalid`, `aria-describedby` or `aria-errormessage` linked to inline error; cross-field/server errors go in a focusable summary linked to fields. Keyboard focus is visibly retained after dialogs and errors. Builder step state, errors and save outcome have text/accessible announcements. Test viewport 320px, desktop, and 400% zoom: selector, filters, cards/list, draft actions, editor and preview remain reachable; horizontally scrollable tables expose headings and a visible scroll hint or use stacked rows. New UI uses semantic OKLCH tokens, all shipped theme variants require legible selected/focus/disabled/status/error states with text indicators (not color alone). Contrast checks are distinct from screenshots. Guard dirty form state on in-app navigation (kind switch, breadcrumb, Back), dialog dismissal and reload; confirm discard or remain, with retained input if navigation is cancelled. Test keyboard-only builder entry, step transitions, component reordering, save/error announcement and exits with a screen reader; run contrast/reflow checks for all shipped themes, including 320px and 400% zoom. No raw rgb or hardcoded role-color conclusions.
