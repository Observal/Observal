# Installed agent and component updates at harness startup — specification and plan

**Status:** In progress: local `freeze`/`unfreeze` policy and registry gate are implemented; the shared comparison verifies exact approved release details. Successful explicit `agent pull` now attempts to capture local file hashes, and a fail-closed Pi user-agent candidate preflight checks consent, component identities, complete locks and unchanged files. A check-only Pi startup worker, bounded comparison cache, durable result spool and Pi UI notification bridge are now implemented; live Pi/RPC verification and race hardening remain open. A standalone, guarded Pi user-agent installer now stages and verifies existing plain profile files and registry-direct script-free skills, serializes against Pi manual pulls and freeze, and rolls back recoverable failures. A separate `_startup-apply` worker now binds its notice/shutdown key to the locally authenticated registry, account and session, limits admission to a 90-second window, reserves 15 seconds before each commit, checks the session shutdown marker under the install gate, and requires a private, fsynced write-ahead outcome record before admitting mutation. It atomically spools verified outcomes (including partial-recovery references) and seals them before clearing the write-ahead record. Pi does not participate in that gate: marker checks are best effort against a concurrent shutdown, not an atomic admission fence. It is launched by the Pi extension only with the temporary `OBSERVAL_PI_AUTO_APPLY=1` pilot gate **and** locally granted `observal unfreeze`; the default startup path remains check-only. An isolated real Pi RPC/local-registry test covers frozen, dirty, unsafe server payload, eligible installation, delayed install/shutdown and next-session replay. The wheel's bundled extension and local extension-source tests pass. Production-profile, TUI/reload, crash/partial recovery and longer network behavior remain to be verified before removing the pilot gate. The Pi extension writes a shutdown marker. Lockfile agent/standalone mutations now re-read and commit under one cross-process lock; reconciliation refuses stale plans instead of replacing concurrent installs. MCP merges, git skills, setup actions and new paths remain notice-only. **Default startup remains check-only; the explicitly gated Pi pilot can install eligible user agents.** `ROADMAP.md` records the agreed opt-in policy. This is about registry agents and components, **not** upgrading the Observal CLI or server, and not about Pi skill collisions or malformed third-party skill files.

## Decision and user contract

- Auto-updating is **off by default**, including for existing users and installations. `observal unfreeze` enables it for this user's **user-scoped, Observal-managed** installations on the active registry; `observal freeze` disables it. Both are idempotent and work offline. “Freeze” refers only to automatic installs: it does **not** create or change a version pin. No change to the semantics of `observal.lock` (a committed agent-version pin) or `~/.observal/lockfile.json` (installed-state evidence).
- A project-scoped install is notice-only unless that specific local project is separately opted in with the proposed `observal unfreeze --project [--dir PATH]`. Require the global `unfreeze` *and* the project grant; `observal freeze --project [--dir PATH]` revokes only that project's grant. Global `freeze` disables all auto-updates without deleting project grants. The grant is **local to this authenticated account and machine**, keyed by normalized registry URL, locally authenticated account ID and resolved project root, and is not committed to the repository. Thus no teammate opts in by merely checking out a project. A project opt-in permits an automatic edit to its committed `observal.lock`; tell the user explicitly at opt-in and on successful update to review/commit the diff. Project updates are a separate rollout gate after user-scope safety is proven.
- `freeze` does not prevent manual installs or suppress update notices. A frozen startup lists available versions and author notes, suggests the **verified** manual command, and says `observal unfreeze` to enable personal auto-updates (or `observal unfreeze --project` for this project, if global unfreeze is already enabled). An unfrozen startup lists changes actually applied and says `observal freeze` to stop future auto-updates. Manual `observal agent pull --upgrade` or a registry install remains available in either state.
- Only new, visible **approved** releases are eligible; never automatically switch registries, downgrade, install an untracked resource, knowingly replace a detected locally modified/unmanaged resource, fill in missing secrets, independently upgrade a component pinned within an agent, or introduce a component absent from the installed agent. Hash rechecks reduce concurrent-edit risk but cannot eliminate the race with an arbitrary filesystem writer. For agents, compare the *complete set of `(component_type, component_id)` identities* in the locally recorded installed lock with the target release's resolved pinned components (including prompts/sandboxes). Every target identity must already be present; missing/ambiguous installed IDs or any added identity makes the agent update notice-only. Removed identities also require manual review (removal/cleanup behavior is not guaranteed), so the first auto-update gate requires **equal identity sets**, although pinned versions/digests may change. A complete strict server lock is necessary but insufficient for this comparison. Respect explicit standalone `requested_version` pins: notify, do not automatically override. Unknown installed versions and missing/inaccessible items are notice-only/diagnostic. If an agent's lock is partial/unlocked or would fail `--strict`, no automatic install.
- Checks and installs are best effort and do not block use of the harness. A notice must never claim an update succeeded merely because a check or a server-side install request succeeded. Clarify whether the current session has loaded new files; otherwise say **“Installed for the next session/reload.”** Never claim that all installed resources are actively used in the session.

### Example TUI copy (illustrative, not exact output contract)

```text
Observal: updated alice/reviewer v1.2.0 → v1.3.0 (Pi, user scope)
  Author's release description: Better review guidance.
  Included component changes: acme/search v2.0.0 → v2.1.0 [if verified from the agent locks]
  Installed for the next session/reload. To turn off automatic updates: observal freeze

Observal: update available acme/linter v1.0.0 → v1.1.0 (project scope; not installed)
  Author's changelog: Handles multi-file patches.
  To update manually: <verified install command with the correct scope and directory>
  To allow automatic project updates here: observal unfreeze --project
```

Suppress an empty/no-changes message on routine startup. In machine/noninteractive mode emit structured results through the integration, not Rich/ANSI or spurious stdout; do not expose paths, credentials, or unbounded release text in hook output. Author-provided descriptions/changelogs are untrusted display text: escape markup and cap display size. If absent, say “No release notes supplied.” When skipping multiple releases, label the target release's notes as such (do not imply they describe every intermediate release).

## Install evidence and legacy eligibility

An approved registry release and a version in `~/.observal/lockfile.json` do **not** establish that on-disk files are unchanged. Before any automatic write, add a versioned local *ownership/baseline manifest* for each `(registry URL, harness, item type/id, scope, resolved installation root)`. Write it only after a **successful explicit/manual** install performed by the new instrumented installer. Record the installed version/digest and the paths actually created or modified, with hashes of the resulting bytes; include the managed key/path and an entire-file hash for merged or shared JSON/TOML/YAML configs. Detect symlink escapes, renamed paths, and two managed items claiming the same path. Keep this manifest outside `observal.lock`, free of file contents and secrets, and use atomic writes plus the same installation lock as the installed-state record. Never treat a layer snapshot (telemetry evidence), registry digest, or a file merely matching a desired release as proof that Observal owns it.

Auto-update eligibility requires the manifest to match the installed-state entry and **every** owned path to match its recorded post-install bytes immediately before writing. A missing, unreadable, symlinked, claimed-by-another-item or dirty path is notice-only with a manual recovery action. For a shared merged file, the initial safe policy is conservative: **any** change to its whole-file hash, even in an unrelated key, makes automatic updates notice-only. First-stage auto-updates must demonstrate a staged merge/replacement that changes only the owned keys and preserves unrelated entries; when the updater cannot prove this, skip it. After a verified successful update, capture new post-install hashes under the same lock. Revalidate **each target immediately before its replacement** and check again during rollback so detected concurrent edits are not overwritten or re-baselined. This is a best-effort boundary, **not immunity to arbitrary concurrent filesystem writes**: an editor could still write in the interval between the final hash and the atomic replace. If rollback cannot fully restore the old state, preserve the original bytes in the private (0700) staging directory, return local target-to-backup recovery references and require manual review rather than deleting the only recovery copy or claiming success.

Existing/legacy installs have no authoritative manifest and remain **notice-only**. Offer an explicit manual reinstall at the recorded version (agents: plain pinned `agent pull` with the correct `--scope`/`--dir`; components: `install --version <installed>` with correct scope/root), using the instrumented installer to establish a new baseline **only if that manual install actually succeeds**. Never automatically adopt legacy files or infer a baseline from the current contents; the user can review any overwrite during manual repair. If a manual install is also unable to establish ownership or integrity, the item remains notice-only. Agent component-set comparison additionally requires trustworthy installed component IDs; missing/ambiguous legacy IDs are not inferred from names.

## Policy/install serialization and effective boundary

Use one **cross-process per-registry policy/install gate** (OS file lock, not the PID/timestamp CLI upgrade lock) shared by `freeze`, `unfreeze`, and *all* automatic install workers. The Pi apply worker also holds a separate registry/account orchestration gate through outcome sealing. Its lock order is **apply-worker gate → registry policy gate → per-installation lock → installed-state/manifest file locks**; freeze takes only the registry gate and manual pulls take only installation/file locks. Policy writes occur under the registry gate, atomically with a durable close/replace; installs may do network discovery *outside* it but must acquire the gate, then the installation lock, re-read policy/installed version/target approval and file baseline, and hold the gate until installation either commits verified files plus metadata or reports a partial failure. No code path may wait for the registry gate while holding an inner lock. A process crash releases OS locks; recovery uses the persisted file/manifest state and skips mismatches. The install worker's 90-second deadline is an admission limit: do not start a mutation that cannot be completed or safely rolled back within the remaining budget. Never terminate the worker forcibly mid-commit.

`observal freeze` returns success **only after** any in-flight automatic install holding that registry gate finishes and the policy-disable write is durable. An install already in progress when `freeze` is invoked may finish **before** `freeze` returns; none may start once `freeze` has returned. If gate acquisition times out or the policy write fails, return a busy/error result, **not** “frozen.” The same boundary applies to `freeze --project`; `unfreeze` never launches installs by itself. Checks and manual installs are not blocked by the policy, but manual installs also coordinate on the relevant installation/file locks to prevent clobbering an automatic install. Bound install time, avoid arbitrary setup commands in automatic mode and test two sessions plus a concurrent freeze against these exact ordering guarantees.

## Proposed CLI and service contract

- Commands: `observal freeze [--project] [--dir PATH] [--output table|json]` and `observal unfreeze [--project] [--dir PATH] [--output table|json]`. `--dir` requires `--project`; default directory for `--project` is CWD. No network is needed to change policy; no installed items are changed by these commands. In human output show effective user/project policy, the relevant registry, and a precise next action. JSON returns a stable object, e.g. `{"registry": "https://…", "scope": "user|project", "project": null, "auto_update": true, "effective": true}`; errors follow `observal_cli/errors.py`. Do not print auth tokens.
- Store local preferences under `~/.observal/` in a **new versioned file**, separated from installed-state and project pins; key both the global grant and project grants by normalized active registry URL **and locally authenticated account ID**. Require a locally stored matching token: account switches, sign-out and environment-only/overridden tokens fail closed. Discard legacy registry-only grants rather than migrating consent to an unknown account. Normalize and resolve the project root consistently with `agent pull --dir`; do not silently opt in nested projects or symlink aliases. Atomic write under a cross-process lock; unknown schema/malformed state must disable automatic updates and surface a repair warning.
- Shared service accepts `(harness, cwd, startup identifier, mode=check|apply, UI capability)` and returns structured per-item results: `type`, registry ID, qualified name, harness, scope, directory (local only), installed version, target version, target release notes, **version availability (`outdated`) separately from install eligibility/verification**, `status` (`current|available|updated|skipped|missing|failed|unknown`), reason/next action, and `effective_in_current_session` (`yes|no|unknown`). A newer version with a pin or unverifiable release remains noticeable, but must not be described as a verified approved release if verification failed. CLI/harness bridges render these safely. Never accept a registry-supplied executable command string as an upgrade instruction.
- Use a bounded TTL for network comparisons (initial target: 24h, tunable only as a separate registry-update setting). Cache *findings*, keyed by registry, user identity, harness, project root and installed-state fingerprint, with atomic writes and expiry; invalidate after install, registry/account change or explicit `outdated`. A cached comparison is **not** install authorization: re-fetch the exact approved target before applying. Rate-limit Inbox reports independently from checks, dedupe notices, and keep UI work non-blocking. Allow explicit `observal outdated` to remain fresh, or document a deliberate `--refresh` option rather than silently changing its semantics.
- Auto-update preflight: verify managed installation, current version, target approval and harness compatibility, stored scope/path, no explicit pin, **equal installed/target agent component-identity sets**, verified clean file baseline, complete agent lock, no missing input/secret or new permission/setup requirement. Build an install plan under the locks described below. Install only via a shared structured installer with atomic/staged writes and backup/rollback where supported. If safe atomicity is not possible, skip, explain why and provide manual steps.
- After applying: compare actual files and installed version, refresh layer evidence only when it matches reality, and record a non-secret audit result. On partial failure preserve repairable details and do not advance the recorded version falsely. No broad catch that hides a failed update as a success.
- Maintain the existing `observal outdated` JSON response and its explicit, best-effort Inbox reporting. If enhancing its suggested command, include actual scope/directory and correct agent `--upgrade`, and clearly label MCP snippet generation. Add `registry skill install --dir PATH` before promising single-command project upgrades. Update bundled Observal skill command docs when adding `freeze`/`unfreeze` or changing manual upgrade syntax.

## Pi result delivery and process lifetime

The Pi extension does not await registry work in `session_start`. On an eligible interactive or RPC startup (`ctx.hasUI`), it launches **one one-shot local worker** with `spawn`/argument array (no shell, no credentials on argv, no ANSI output), keyed by registry/harness/session. Default check-only mode has a **10-second wall-clock budget** and can be killed. `OBSERVAL_PI_AUTO_APPLY=1` selects the apply pilot, which has a **90-second admission deadline** including lock wait and a reserved recovery window; it is detached and must not be killed during mutation. Network waits can overrun the admission deadline, but mutation is refused if too little time remains; measure this against real agent pulls (do not reuse the Pi telemetry 5-second per-request timeout as a whole-install budget). There is no persistent daemon. The worker is responsible for persisting a size-limited, versioned, secret-free JSON result via atomic rename to `~/.observal/update-notices/` **before** it exits. The extension reads only this local result and displays notices through `ctx.ui.notify`; the child stdout/stderr is suppressed or captured with strict byte limits and never interpreted as a Pi hook protocol response. Local outcome-spool files are mode 0600 and keyed by registry/user/session; dedupe each result once, retain until delivered, expire old results, and cap total size/count. Before any automatic mutation, the worker atomically reserves and fsyncs a same-session `.pending` outcome journal under the private notice directory. If that fails, the install is skipped. After verified commit or recovery, the final notice and completion seal are each fsynced before the journal can be removed. A full/unwritable spool, crash or failed final/seal write leaves the `.pending` record in place: the bridge warns that files **may have changed**, never claims success, and never consumes the journal. A separate cross-process **registry/account apply-worker gate** serializes the initial unresolved-journal check, reservations, installer calls and final outcome sealing across Pi sessions. Its acquisition precedes the policy gate (which still precedes the Pi installation lock); freeze and manual pulls do not acquire this outer gate. The second worker therefore cannot pass its initial check until the first worker has either sealed its outcome or left an unresolved journal. Subsequent workers refuse new installs for that registry/account until an unresolved journal is reconciled. These unresolved records are not expired or pruned; after manually verifying installed files and metadata, a user can remove the indicated local record. A crashed/timed-out worker records no success and leaves a visible diagnostic for the next interactive startup where possible. The updater must not continue a new install past its deadline; if commit/rollback cannot be safely bounded, skip automatic installation at preflight.

While the same Pi session is alive, a short-lived timer/poll (or child completion notification) consumes the result and notifies the UI. On `session_shutdown`, the extension writes an atomic, session-keyed shutdown marker, cancels polling and prevents notification through stale contexts; it must **not** kill a worker in the middle of a file write. The worker first verifies its marker key against the active registry, account and session ID, then checks that marker **under the policy/install gate** as close as practical to the first file replacement. A marker visible at that check prevents admission and produces a notice-only result. The Pi shutdown writer does **not** acquire the same gate: shutdown racing after the final check, even before the first replacement, may still result in a completed and verified install. Once replacements begin, the one-shot worker finishes verification or recovery after Pi exits rather than interrupting mutation; the 90-second limit is an admission deadline, not a forced commit kill. The durable result is shown at the **next interactive/RPC startup**, labelled with the prior session/time and whether a reload is needed. On a hard process crash without a shutdown marker, the worker may still finish; never claim it updated the departed session. On next startup drain previously completed notices before launching another check; atomically mark delivered only after `ctx.ui.notify` returns without error. Revalidate policy at install commit so a late worker cannot bypass `freeze`.

In Pi print/JSON modes (`!ctx.hasUI`), do **not** start automatic installs: there may be no UI or reliable time to deliver their outcome. An explicit `observal outdated --output json` remains the machine-readable check path. In RPC with a supported UI, use `ctx.ui.notify` and the same durable spool; if the client disconnects, leave undelivered results for the next interactive/RPC session. Do not inject update results as model/user prompts, print to arbitrary stdout, or promise a notice in a session that ends before the check completes. Test Pi's live UI and RPC/print behavior, process cancellation/crash, stale result replay, duplicate events and startup shutdown races.

## Harness and IDE integration plan

There is **no universal startup callback**. Each adapter/bridge must prove that it can (a) identify harness and CWD, (b) run exactly once per session or bounded interval without stalling startup, (c) render an actionable notice, and (d) distinguish installed-from-active resources. Reuse one Python updater and existing installers; don't copy comparison logic into plugins. The startup bridge must not turn a telemetry failure into an installation attempt, and telemetry must not depend on an update succeeding.

1. **Pi pilot:** use the existing extension `session_start` (`packages/pi-extension/extensions/observal.ts`) as the UI trigger; use the one-shot worker and durable result contract above. On `startup`/`resume`, dedupe by session/TTL; `ctx.ui.notify` when `ctx.hasUI`, but suppress installs in UI-less modes. Do not block Pi startup on registry access or reload from a lifecycle handler. Decide how to refresh active user profile files (currently copied by `/agent`) before promising that an updated profile is active. Test the bundled-local and npm extension packaging paths (`observal_cli/pi_extension.py`).
2. **Other terminal harnesses:** inventory real installed hook/plugin surfaces rather than assuming registry `hook_events_map` means an event is actually wired. `claude-code` and `codex` currently use `UserPromptSubmit`/`Stop`; Kiro standalone hooks use `UserPromptSubmit`/`Stop` (the registry maps SessionStart to `agentSpawn`, but the installed spec does not); Copilot CLI and Goose have start events; OpenCode has `session.created`; Antigravity uses `PreInvocation`/`Stop`. Cursor has no declarative hook spec (its doctor writes a separate bridge). Hook stdout may have protocol meaning: report only through host-supported user UI or a safe side channel. On hosts whose earliest reliable event is first prompt, label the check accordingly, not “before startup.” Extend `doctor patch` and cleanup/tests to install and remove **only** Observal-owned hooks.
3. **IDE phase:** verify Kiro IDE, Cursor and VS Code Copilot host lifecycle and user-notification APIs individually in a running host. An IDE may keep files/MCPs in memory; edits can require a host reload and must never be described as active immediately. If a host lacks a reliable startup/event UI, use an opt-in companion/plugin or offer notices on the earliest supported event; do not claim automatic startup coverage without testing it.

## Rollout gates and tests

1. **Policy + docs:** `ROADMAP.md` records opt-in auto-updating and separate project consent. CLI policy/gate, help and core skill/reference docs are in place; complete manual-upgrade guidance and verify the CLI/JSON contracts across supported platforms.
2. **Shared check:** `installed_updates.py` now shares comparison with `outdated` while retaining its JSON results, and optionally validates exact release status/harness/notes for a future startup caller. A 24-hour check-only cache and bounded error spool are implemented; finish integration tests for missing/archived/private/pending/owner-visible releases, prerelease, unknown, wrong registry, malformed lockfile, scoped paths, explicit pins, multiple harnesses, and Inbox dedupe.
3. **Personal installs:** CLI policy and a v2 ownership baseline (requiring a matching lock digest) on a successful **manual** agent pull are in place; earlier baselines require another explicit pull. Pi user-agent preflight and a narrow guarded installer with strict target-file plan comparison are implemented; an experimental Pi-only startup bridge launches apply only under `OBSERVAL_PI_AUTO_APPLY=1` plus local unfreeze. Then extend to user-scope skills after source/path safety tests. Legacy installs with no verified baseline stay notice-only. 5. **Other harnesses and IDEs:** for each supported harness, test in the real host on its supported OS surfaces; verify notices, appropriate restart messaging and safety checks. Review startup latency and failure rates before enabling project grants.
6. **Project gate:** only after safe scoped installs exist, implement local `--project` grant and verify tracked `observal.lock` diffs, team checkout behavior, concurrent editing, rollback, and clear manual fallback. Do not silently opt in other users, worktrees or projects.

### Explicit out-of-scope items

Observal CLI self-upgrade (`observal self`), server upgrades, unmanaged harness resources, retroactively changing an agent release's component pins, auto-enabling new components for an agent not previously installed, Pi skill-location collisions/frontmatter repair, and background update daemons independent of a harness session.
