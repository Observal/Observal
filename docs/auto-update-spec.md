# Installed agent and component updates at harness startup — specification and plan

**Status:** Pi startup is check-only by default. With `observal unfreeze` as the sole user-level opt-in, Pi startup reuses the normal `agent pull --version --strict --no-prompt` command through the shared runner under account/registry consent. The normal pull checks fresh pin intent, the generated component lock against the approved exact release, the v3 owned-file baseline (bytes and modes) and a narrow Pi file plan before writing, then records the new baseline; the worker verifies the exact release lock and files before reporting success. The existing registry/account policy gates, detached Pi worker, bounded network admission, private `.pending` notice and next-session delivery remain. The old Pi-only installer and its separate writer were removed. **The normal installer is not transactional.** A shared recovery helper saves exact owned bytes/modes and planned hashes/modes before an automatic write; when a stopped installer leaves the original metadata intact and every managed file matches either its old or planned bytes **and mode**, it restores the original files under the install lock. Otherwise it retains the private backup and unsealed pending notice for manual inspection, blocking future automatic attempts. Isolated live Pi RPC/TUI tests cover frozen/dirty installs, unsafe releases, timeouts, shutdown, SIGKILL before and after a file write, verified saved-profile updates and `/agent` activation. The pilot remains off by default and is not approved for production profiles. The explicit `observal update --all [--yes]` also runs normal agent/skill/hook installers; it is manual and not governed by freeze. MCP installs still print a snippet by default. `registry mcp install --harness pi --managed` now explicitly writes a credential-free Pi user MCP entry into an entirely Observal-owned global file; it will not adopt an existing pasted file. Only approved, unchanged, unpinned managed entries in that file are eligible at Pi startup, using the normal managed writer and the shared conditional whole-file recovery plan. Project auto-install remains disconnected. The first standalone component shape is now wired into Pi startup: existing registry-direct user skills with `SKILL.md` and at most one previously installed script, using the instrumented normal `registry skill install` command. Manual installs record exact `SKILL.md` bytes/mode and known pin intent; the guarded normal installer checks an approved exact version, matching install payload, ownership, unchanged mode/content and an unshared, unchanged file set before saving a conditional backup and writing. The worker verifies the new lock and baseline before reporting success. A disposable-home real Pi RPC run confirms the skill's frozen notice and opted-in update through the installed extension and worker; this does not prove that a skill already loaded in the current Pi session is refreshed. Git skills, newly introduced scripts, extra files, shared paths, project skills and unsupported harnesses remain notice-only. A Claude Code bridge installed through `observal doctor patch --harness claude-code` now starts a detached, gated worker on `SessionStart`; a later prompt delivers sealed results as a user-facing `systemMessage`, never model context. `SessionEnd` marks shutdown without waiting for or killing a worker. Only an existing, singly owned, component-free Claude Code **user agent** with one `~/.claude/agents/<local_name>.md` profile and a v3 bytes-and-modes baseline is eligible when the same account explicitly runs `observal unfreeze`. The normal strict pull is guarded by fresh pin/approved-release checks, a generated exact single-file plan, verification that the server’s delegation MCP registration already exists unchanged (so setup is never run automatically), a cross-registry Claude install lock and shared conditional recovery. The worker checks installed lock/baseline and planned target bytes/mode before reporting an on-disk update; a new Claude session must select the saved agent (for example, `claude --agent <local_name>`) to load that profile. A disposable-home subprocess test covers frozen/opted-in installs, dirty modes, pins, extra outputs and stopped writes with conditional recovery. A separate disposable-home test confirms `SessionEnd` blocks write admission. **Pi extension and hooks:** Pi has no registry-hook install path (empty event map; hook CLI is project-only), so there is nothing to auto-update there. Observal's own bundled Pi telemetry extension is refreshed at startup only after `unfreeze`, only when its manifest records a SHA-256 that matches the file on disk (older manifests, edited or foreign files stay manual via `observal doctor patch`), and takes effect on the next Pi load.

**Claude Code standalone skills:** the Pi skill guard is generalized to `~/.claude/skills/<name>/` (registry-direct `SKILL.md` plus at most one already-owned script) under the cross-registry Claude install lock, with the same consent, pin, ownership, mode and conditional-recovery checks; a new session is needed to load it. Claude standalone hooks are project-scoped and Claude MCPs register via `claude mcp add` into shared config, so both stay manual until project consent and entry-level ownership exist. Claude agents may now bundle already-owned registry-direct skills (with at most one script each) and hook scripts alongside the profile: the plan predicts every file and mode, rejects added/removed files, git skills, custom paths, shared names and any MCP setup other than the verified delegation no-op. Bundled MCP entries remain manual.

**Skipped-update reasons:** every refusal is reported with its reason in both hosts (Pi shows `item.reason`; the Claude hook now appends `Reason: …`). Parent-side checks supply specific text (edited file, ownership conflict, pin); the child installer records its own fixed, sanitized refusal message (added/removed files, git skill, custom path, name collision, unsupported MCP setup) through a private `.reason` file. Only our own ValueError messages are recorded, never OS error text or paths.

**Added and removed files:** a release may now add or drop skill and hook components for Pi and Claude Code agents. A new file is created only if its path does not exist, is not a symlink and is not in any other install's ownership baseline; the recovery record stores it as a *create* row (a failed install deletes it again only if it still matches the planned bytes and mode). A dropped file is deleted only when the verified baseline proves it unedited and it lies under the agent's skills/hooks area; the recovery record keeps its bytes as a *delete* row. Profiles, `mcp.json` and anything outside skills/hooks are never removed, edits and name collisions still block the whole update, and MCP component changes stay manual. Every refusal is reported with its reason.

**Claude Code managed MCPs:** `registry mcp install --harness claude-code --managed` (credential-free stdio only) runs Claude's own `claude mcp add -s user` and records a private, per-entry ownership record of the exact entry that resulted; Observal never edits `~/.claude.json`, refuses a name that already exists (pasted entries are never adopted) and a nonstandard `CLAUDE_CONFIG_DIR`. At startup, after `unfreeze`, an unpinned entry whose live value still equals the record is replaced with `claude mcp remove` then `add`; the plan (old and new entry) is saved first, and a stopped run restores the original by re-adding it only when the entry is absent or already the planned one — an edited (foreign) entry is left alone and reported. This was exercised against a fake `claude` CLI in disposable homes; real-CLI behavior must be confirmed in the thorough-testing phase.

**Agent MCP changes:** for Pi, a release may add, drop or re-version MCPs in an agent's own isolated `mcp.json`. The file must still match its ownership baseline; the plan is the release's exact server set, applied by the normal writer and then rewritten to those bytes if the merge left a dropped entry behind; dropping every MCP deletes the unedited file. An added MCP must be a plain local server (no URL, headers or env values, other than the agent's own public id), otherwise the update stays manual and says why. Claude Code registers an agent's MCPs per project directory (local scope in `~/.claude.json`), so MCP changes there stay manual until project scope is decided.

**Credentials (Pi):** an agent's own `mcp.json` and a managed standalone Pi MCP may carry credentials the user already saved. At startup the saved values are re-supplied to the normal install request; the plan then requires every credential in the result to be byte-identical to the saved one (empty placeholders are not credentials). A changed, new or missing required value stays manual with a stated reason; notices never include values. Claude Code's generated MCP command cannot carry credentials Observal can verify, so credential-bearing Claude MCPs stay manual and say so.

**Observal's own Claude Code hooks:** `observal doctor patch` records a private (0600) hash of every hook group it writes into `~/.claude/settings.json` (only when the groups equal what the spec generates). After `unfreeze`, the Claude startup worker replaces only groups that still match that record with the shipped spec, keeping foreign hooks and every other setting, with an atomic write that is abandoned if Claude changed the file in the meantime. It never installs hooks for someone who has none, never adopts an unrecorded or edited group, and says why in a one-time message (shown once per outcome and spec version). Loaded sessions keep the hooks they started with; a new session loads the update.

## Decision and user contract

- Auto-updating is **off by default**, including for existing users and installations. `observal unfreeze` enables it for this user's **user-scoped, Observal-managed** installations on the active registry; `observal freeze` disables it. Both are idempotent and work offline. “Freeze” refers only to automatic installs: it does **not** create or change a version pin. No change to the semantics of `observal.lock` (a committed agent-version pin) or `~/.observal/lockfile.json` (installed-state evidence).
- A project-scoped install is notice-only unless that specific local project is separately opted in with the proposed `observal unfreeze --project [--dir PATH]`. Require the global `unfreeze` *and* the project grant; `observal freeze --project [--dir PATH]` revokes only that project's grant. Global `freeze` disables all auto-updates without deleting project grants. The grant is **local to this authenticated account and machine**, keyed by normalized registry URL, locally authenticated account ID and resolved project root, and is not committed to the repository. Thus no teammate opts in by merely checking out a project. A project opt-in permits an automatic edit to its committed `observal.lock`; tell the user explicitly at opt-in and on successful update to review/commit the diff. Project updates are a separate rollout gate after user-scope safety is proven.
- `freeze` does not prevent manual installs or suppress update notices. A frozen startup lists available versions and author notes, suggests the **verified** manual command, and says `observal unfreeze` to enable personal auto-updates (or `observal unfreeze --project` for this project, if global unfreeze is already enabled). An unfrozen startup lists changes actually applied and says `observal freeze` to stop future auto-updates. Manual `observal agent pull --upgrade` or a registry install remains available in either state.
- Only new, visible **approved** releases are eligible; never automatically switch registries, downgrade, install an untracked resource, knowingly replace a detected locally modified/unmanaged resource, fill in missing secrets, independently upgrade a component pinned within an agent, or introduce a component absent from the installed agent. Hash rechecks reduce concurrent-edit risk but cannot eliminate the race with an arbitrary filesystem writer. For agents, compare the *complete set of `(component_type, component_id)` identities* in the locally recorded installed lock with the target release's resolved pinned components (including prompts/sandboxes). Every target identity must already be present; missing/ambiguous installed IDs or any added identity makes the agent update notice-only. Removed identities also require manual review (removal/cleanup behavior is not guaranteed), so the first auto-update gate requires **equal identity sets**, although pinned versions/digests may change. A complete strict server lock is necessary but insufficient for this comparison. Respect explicit standalone `requested_version` pins: notify, do not automatically override. Unknown installed versions and missing/inaccessible items are notice-only/diagnostic. If an agent's lock is partial/unlocked or would fail `--strict`, no automatic install.
- Checks and installs are best effort and do not block use of the harness. A notice must never claim an update succeeded merely because a check or a server-side install request succeeded. Clarify whether the current session has loaded new files; otherwise say **“Installed for the next session/reload.”** Never claim that all installed resources are actively used in the session.

## Install evidence and legacy eligibility

An approved registry release and a version in `~/.observal/lockfile.json` do **not** establish that on-disk files are unchanged. Before any automatic write, add a versioned local *ownership/baseline manifest* for each `(registry URL, harness, item type/id, scope, resolved installation root)`. Write it only after a **successful explicit/manual** install performed by the new instrumented installer. Record the installed version/digest and the paths actually created or modified, with hashes of the resulting bytes; include the managed key/path and an entire-file hash for merged or shared JSON/TOML/YAML configs. Detect symlink escapes, renamed paths, and two managed items claiming the same path. Keep this manifest outside `observal.lock`, free of file contents and secrets, and use atomic writes plus the same installation lock as the installed-state record. Never treat a layer snapshot (telemetry evidence), registry digest, or a file merely matching a desired release as proof that Observal owns it.

Auto-update eligibility requires the manifest to match the installed-state entry and **every** owned path to match its recorded post-install bytes **and mode** before the normal installer writes. Hash-only v2 baselines remain notice-only until a manual re-pull captures v3 mode evidence. Dirty, unowned, symlinked, shared, or newly introduced paths remain notice-only. The Claude Code plan accepts only one existing user-profile path, no component files or shared config writes; it admits the server-added `observal-agents` setup command only if the exact project-local Claude registration already exists, then removes that *proved no-op* command before invoking the normal profile writer. Missing or changed MCP registration and a nonstandard `CLAUDE_CONFIG_DIR` stay manual. It checks another agent’s display and local names even if that agent has no baseline. The Pi startup plan accepts existing profiles, same-key updates to their isolated owned MCP config, and registry-direct skills whose entire `SKILL.md`/single-script file set is already owned and unchanged; new MCP entries, git skills, setup commands, and new paths remain manual. The deployed server also generates an `observal-agents` entry in every Pi profile’s isolated `mcp.json`: an unchanged, wholly owned config is a verified no-op; an existing config whose exact set of MCP keys is unchanged can update the approved reference through the normal merge writer, with planned bytes and replacement mode checked afterward. New or removed entries, foreign keys, new paths, and shared MCP settings remain manual. The normal pull rechecks the fresh local pin and compares the actual generated component lock with the approved version response inside Pi's install lock before writing. After the normal installer succeeds, capture new hashes and modes under Pi's installation lock and verify the exact release lock and files. This is a best-effort check against external filesystem races; it cannot make arbitrary concurrent edits atomic. The reusable recovery helper backs up only a complete, owned file plan before mutation, with a size cap and durable private manifest. It restores a failed install only when metadata still matches the old record and all files match old or planned bytes **and modes** under the installation lock. Pi's tempfile-based profile writer has a measured target mode (accounting for umask); existing direct skill writes and an unchanged delegation config retain their old modes. An unknown target mode, unexpected chmod, unfamiliar bytes, advanced lock or baseline, or incomplete record keeps the backup and durable pending notice for manual inspection; this is a conditional recovery, not a transactional guarantee. Other harnesses and components must first provide complete managed paths and exact planned bytes to use this helper; it does not enable their startup installs. The Claude profile plan uses the normal atomic writer’s target mode and compares the resulting bytes/mode with the durable plan, not merely the newly captured baseline.

Existing/legacy installs have no authoritative manifest and remain **notice-only**. Offer an explicit manual reinstall at the recorded version (agents: plain `agent pull` without `--version` for unpinned user installs, using the correct `--scope`/`--dir`; components: `install --version <installed>` with correct scope/root), using the instrumented installer to establish a new baseline **only if that manual install actually succeeds**. Never automatically adopt legacy files or infer a baseline from the current contents; the user can review any overwrite during manual repair. If a manual install is also unable to establish ownership or integrity, the item remains notice-only. Agent component-set comparison additionally requires trustworthy installed component IDs; missing/ambiguous legacy IDs are not inferred from names.

## Policy/install serialization and effective boundary

Use one **cross-process per-registry policy/install gate** (OS file lock, not the PID/timestamp CLI upgrade lock) shared by `freeze`, `unfreeze`, and *all* automatic install workers. The Pi apply worker also holds a separate registry/account orchestration gate through outcome sealing. Its lock order is **apply-worker gate → registry policy gate → per-installation lock → installed-state/manifest file locks**; freeze takes only the registry gate and manual pulls take only installation/file locks. Policy writes occur under the registry gate, atomically with a durable close/replace; installs may do network discovery *outside* it but must acquire the gate, then the installation lock, re-read policy/installed version/target approval and file baseline, and hold the gate until installation either commits verified files plus metadata or reports a partial failure. No code path may wait for the registry gate while holding an inner lock. A process crash releases OS locks; recovery uses the persisted file/manifest state and skips mismatches. The 90-second limit bounds admission and registry work, not an already started write. Never terminate the installer subprocess forcibly mid-commit; a failed or interrupted write may leave a pending outcome for manual review.

`observal freeze` returns success **only after** any in-flight automatic install holding that registry gate finishes and the policy-disable write is durable. An install already in progress when `freeze` is invoked may finish **before** `freeze` returns; none may start once `freeze` has returned. If gate acquisition times out or the policy write fails, return a busy/error result, **not** “frozen.” The same boundary applies to `freeze --project`; `unfreeze` never launches installs by itself. Checks and manual installs are not blocked by the policy, but manual installs also coordinate on the relevant installation/file locks to prevent clobbering an automatic install. Bound install time, avoid arbitrary setup commands in automatic mode and test two sessions plus a concurrent freeze against these exact ordering guarantees.

## Proposed CLI and service contract

- Commands: `observal freeze [--project] [--dir PATH] [--output table|json]` and `observal unfreeze [--project] [--dir PATH] [--output table|json]`. `--dir` requires `--project`; default directory for `--project` is CWD. No network is needed to change policy; no installed items are changed by these commands. In human output show effective user/project policy, the relevant registry, and a precise next action. JSON returns a stable object, e.g. `{"registry": "https://…", "scope": "user|project", "project": null, "auto_update": true, "effective": true}`; errors follow `observal_cli/errors.py`. Do not print auth tokens.
- Store local preferences under `~/.observal/` in a **new versioned file**, separated from installed-state and project pins; key both the global grant and project grants by normalized active registry URL **and locally authenticated account ID**. Require a locally stored matching token: account switches, sign-out and environment-only/overridden tokens fail closed. Discard legacy registry-only grants rather than migrating consent to an unknown account. Normalize and resolve the project root consistently with `agent pull --dir`; do not silently opt in nested projects or symlink aliases. Atomic write under a cross-process lock; unknown schema/malformed state must disable automatic updates and surface a repair warning.
- Shared service accepts `(harness, cwd, startup identifier, mode=check|apply, UI capability)` and returns structured per-item results: `type`, registry ID, qualified name, harness, scope, directory (local only), installed version, target version, target release notes, **version availability (`outdated`) separately from install eligibility/verification**, `status` (`current|available|updated|skipped|missing|failed|unknown`), reason/next action, and `effective_in_current_session` (`yes|no|unknown`). A newer version with a pin or unverifiable release remains noticeable, but must not be described as a verified approved release if verification failed. CLI/harness bridges render these safely. Never accept a registry-supplied executable command string as an upgrade instruction.
- Use a bounded TTL for network comparisons (initial target: 24h, tunable only as a separate registry-update setting). Cache *findings*, keyed by registry, user identity, harness, project root and installed-state fingerprint, with atomic writes and expiry; invalidate after install, registry/account change or explicit `outdated`. A cached comparison is **not** install authorization: re-fetch the exact approved target before applying. Rate-limit Inbox reports independently from checks, dedupe notices, and keep UI work non-blocking. Allow explicit `observal outdated` to remain fresh, or document a deliberate `--refresh` option rather than silently changing its semantics.
- Auto-update preflight: verify managed installation, current version, target approval and harness compatibility, stored scope/path, no explicit pin, **equal installed/target agent component-identity sets**, verified clean file baseline, complete agent lock, no missing input/secret or new permission/setup requirement. Build an install plan under the locks described below. Invoke the existing installer with a structured argv, not a shell command; perform the managed-path and baseline check inside its write boundary. A failed install is not a successful update even when a few files changed; report uncertainty and keep its pending record.
- After applying: compare actual files and installed version, refresh layer evidence only when it matches reality, and record a non-secret audit result. On partial failure preserve repairable details and do not advance the recorded version falsely. No broad catch that hides a failed update as a success.
- Maintain the existing `observal outdated` JSON response and its explicit, best-effort Inbox reporting. If enhancing its suggested command, include actual scope/directory and correct agent `--upgrade`, and clearly label MCP snippet generation. Add `registry skill install --dir PATH` before promising single-command project upgrades. Update bundled Observal skill command docs when adding `freeze`/`unfreeze` or changing manual upgrade syntax.

## Pi result delivery and process lifetime

The Pi extension does not await registry work in `session_start`. UI-capable sessions launch a one-shot worker with an argument array, no shell and no credentials on argv. Pi always launches the detached worker for interactive sessions: frozen accounts receive notices only, while unfreezing enables eligible installs. Its 90-second **admission** deadline never kills an installer that may write. Registry requests, including retry waits and trickling responses, are bounded before write admission. The worker reserves and fsyncs a private `.pending` notice before launching the shared runner. It rechecks consent, exact release, stored version, component identities and owned-file hashes; the normal pull checks again just before writing. Successful file/lock verification seals a private notice; a failed child whose original files and lock can be verified unchanged is a skip. When a failed child can be safely attributed to the planned bytes **and file modes**, and old metadata bytes/modes are unchanged, the shared helper restores verified original bytes/modes and seals a skipped/failed-update notice. Otherwise the unsealed pending notice reports uncertainty, points to the private backup when one exists, and blocks later auto-installs for that account/registry until manual inspection. This path never claims universal rollback or restores over unrecognized edits. Notices are delivered in a UI-capable session, including later sessions after Pi exits; they never claim that a saved profile is active until `/agent` re-selection and reload.

While the same Pi session is alive, a short-lived timer/poll (or child completion notification) consumes the result and notifies the UI. On `session_shutdown`, the extension writes an atomic, session-keyed shutdown marker, cancels polling and prevents notification through stale contexts; it must **not** kill a worker in the middle of a file write. The worker first verifies its marker key against the active registry, account and session ID, then checks that marker **under the policy/install gate** as close as practical to the first file replacement. A marker visible at that check prevents admission and produces a notice-only result. The Pi shutdown writer does **not** acquire the same gate: shutdown racing after the final check, even before the first replacement, may still result in a completed and verified install. Once replacements begin, the one-shot worker finishes verification or records an uncertain partial outcome after Pi exits rather than interrupting mutation; the 90-second limit is an admission deadline, not a forced commit kill. The durable result is shown at the **next interactive/RPC startup**, labelled with the prior session/time and whether a reload is needed. On a hard process crash without a shutdown marker, the worker may still finish; never claim it updated the departed session. On next startup drain previously completed notices before launching another check; atomically mark delivered only after `ctx.ui.notify` returns without error. Revalidate policy at install commit so a late worker cannot bypass `freeze`.

In Pi print/JSON modes (`!ctx.hasUI`), do **not** start automatic installs: there may be no UI or reliable time to deliver their outcome. An explicit `observal outdated --output json` remains the machine-readable check path. In RPC with a supported UI, use `ctx.ui.notify` and the same durable spool; if the client disconnects, leave undelivered results for the next interactive/RPC session. Do not inject update results as model/user prompts, print to arbitrary stdout, or promise a notice in a session that ends before the check completes. Test Pi's live UI and RPC/print behavior, process cancellation/crash, stale result replay, duplicate events and startup shutdown races.

## Harness and IDE integration plan

There is **no universal startup callback**. Each adapter/bridge must prove that it can (a) identify harness and CWD, (b) run exactly once per session or bounded interval without stalling startup, (c) render an actionable notice, and (d) distinguish installed-from-active resources. Reuse one Python updater and existing installers; don't copy comparison logic into plugins. The startup bridge must not turn a telemetry failure into an installation attempt, and telemetry must not depend on an update succeeding.

1. **Pi pilot:** use the existing extension `session_start` (`packages/pi-extension/extensions/observal.ts`) as the UI trigger; use the one-shot worker and durable result contract above. On `startup`/`resume`, dedupe by session/TTL; `ctx.ui.notify` when `ctx.hasUI`, but suppress installs in UI-less modes. Do not block Pi startup on registry access or reload from a lifecycle handler. Decide how to refresh active user profile files (currently copied by `/agent`) before promising that an updated profile is active. Test the bundled-local and npm extension packaging paths (`observal_cli/pi_extension.py`).
2. **Other terminal harnesses:** inventory real installed hook/plugin surfaces rather than assuming registry `hook_events_map` means an event is actually wired. `claude-code` installs a gated detached `SessionStart` worker plus `SessionEnd` shutdown marking alongside its `UserPromptSubmit`/`Stop` telemetry hooks; `codex` currently uses `UserPromptSubmit`/`Stop`; Kiro standalone hooks use `UserPromptSubmit`/`Stop` (the registry maps SessionStart to `agentSpawn`, but the installed spec does not); Copilot CLI and Goose have start events; OpenCode has `session.created`; Antigravity uses `PreInvocation`/`Stop`. Cursor has no declarative hook spec (its doctor writes a separate bridge). Hook stdout may have protocol meaning: report only through host-supported user UI or a safe side channel. On hosts whose earliest reliable event is first prompt, label the check accordingly, not “before startup.” Extend `doctor patch` and cleanup/tests to install and remove **only** Observal-owned hooks.
3. **IDE phase:** verify Kiro IDE, Cursor and VS Code Copilot host lifecycle and user-notification APIs individually in a running host. An IDE may keep files/MCPs in memory; edits can require a host reload and must never be described as active immediately. If a host lacks a reliable startup/event UI, use an opt-in companion/plugin or offer notices on the earliest supported event; do not claim automatic startup coverage without testing it.

## Rollout gates and tests

1. **Policy + docs:** `ROADMAP.md` records opt-in auto-updating and separate project consent. CLI policy/gate, help and core skill/reference docs are in place; complete manual-upgrade guidance and verify the CLI/JSON contracts across supported platforms.
2. **Shared check:** `installed_updates.py` now shares comparison with `outdated` while retaining its JSON results, and optionally validates exact release status/harness/notes for a future startup caller. A 24-hour check-only cache and bounded error spool are implemented. Gated Pi apply compares releases fresh before selecting candidates (even when a pre-release check-only result is cached), and the normal installer re-fetches the exact approved release under its lock. A failed fresh comparison never falls back to cached data for installation. Finish integration tests for missing/archived/private/pending/owner-visible releases, prerelease, unknown, wrong registry, malformed lockfile, scoped paths, explicit pins, multiple harnesses, and Inbox dedupe.
3. **Personal installs:** The opt-in Pi user-agent pilot reuses the normal agent installer with a pre-write v3 file-baseline and existing-file plan. An isolated live Pi/RPC/TUI test covers dirty files, frozen notices, unsafe releases, long retries, trickling responses, shutdown, SIGKILL before and after replacement, verified lock/baseline updates, and `/agent` activation. A disposable profile against internal.observal.io 1.13.1 also confirmed a real v1.0.0 → v1.0.1 component-free approved release through manual pull, check-only, gated apply, saved-vs-active behavior and `/agent` activation; its synthetic agent was archived afterward. After a post-write crash, the worker can restore from a private backup only if the current file bytes/modes match old or planned evidence and the lock/baseline metadata remains unchanged; otherwise it retains the backup and pending notice for manual inspection. Production-profile and power-loss behavior have not been approved. Keep the account frozen on production profiles until the pilot is reviewed. Legacy user-agent entries without an ownership baseline **or explicit pin-intent metadata**, project installs, MCPs, and standalone installs other than the narrow Pi user-skill shape remain notice-only at startup. A plain explicit manual re-pull (without `--version`, which otherwise creates a pin) keeps the installed version and records unpinned intent; `--version` pins the user install and remains notice-only, while a later explicit `--upgrade` clears that pin. Expand only after establishing managed write-and-track paths, project pin handling, and actual host startup surfaces.

## Enumerated pilot, and what is deliberately deferred

This section is the authoritative list of what the pilot updates automatically (after `observal unfreeze`, only for installs with a verified ownership baseline, known unpinned intent, and an exact approved release). Earlier prose in this document describes the order slices were built in and may be narrower; where they differ, this list wins. Everything not listed stays notice-only, with the reason shown to the user.

| Shape | Pi | Claude Code |
|---|---|---|

| Agent's bundled registry-direct skills (at most one script each); skills added or dropped by a release | yes | yes |

**Deferred, each with the gate it must meet**

1. **Project scope** (separate follow-up PR). Initial gate: *untracked, baseline-owned project installs*.
   - Consent is per canonical project directory, recorded only under `~/.observal`, never inferred from the repository or from user-level consent. Worktrees are separate directories and separate consents.
   - Sessions started in a subdirectory resolve to the one recorded install root; ambiguous nested installs and path aliases are refused.
   - A prior local ownership baseline is still required: untracked does not mean Observal-owned.
   - Git tracking of every planned path and of `observal.lock` is checked at admission and again immediately before writing; if Git status cannot be established the update is refused. Tracked files and a tracked `observal.lock` stay notice-only. This is a rollout limit, not a claim that tracked installs can never be supported, and it establishes only that this automatic write is not changing something Git currently tracks.
   - New piece: an entry-level update of our own entry in `observal.lock`, with compare-and-swap and a recovery row that restores only that entry.
2. **Claude agent MCPs (local scope).** Claude registers a pulled agent's MCPs in `~/.claude.json` under `projects[<dir>]`, a file Claude itself rewrites and which also holds other projects' entries and credentials. They stay manual until all of the following exist: (a) the pull records the exact entries it created, so legacy unrecorded entries stay manual; (b) a verified command-effect model for `claude mcp add/remove -s local` run from the install directory; (c) serialization with manual changes, or detection that one happened; (d) a before/after comparison proving no other project's or user's entry changed; (e) a recovery journal covering multiple entries that is joined to the agent's file journal and re-adds only our entries, never restoring file bytes; and (f) an explicit statement of the window between `remove` and `add`. Credential-bearing entries stay manual.
3. **Credential-bearing Claude MCPs.** Claude's generated command cannot carry values Observal can verify without storing them.
4. **The other eight harnesses.** One at a time, each needing a verified startup surface, an exact plan, and a real host test.
5. **Tracked project installs, standalone project skills, MCPs and hooks, and other pasted or unmanaged config.**

### Explicit out-of-scope items
